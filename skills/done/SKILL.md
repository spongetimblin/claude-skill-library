# done

The user wants to leave this session knowing nothing will fall through the cracks. Find out whether they can, and tell them plainly.

What they added: $ARGUMENTS

Count anything they say they did, and check it where you can. Leave out anything they say they're skipping or already know about. If they name a scope, check only that; otherwise check the whole session.

## Check

1. Read the whole session. Run `python3 ~/.claude/skills/done/scripts/session_text.py --out <your scratchpad folder>/session_text.txt`, which prints any turns that were summarized out of your context, since early requests may be missing from it. If it says nothing was summarized, you already have everything. If those turns are too long to print, it saves them to that file and prints only the user's messages, one line each: list the requests from those, and grep the file for what Claude said it would do. The script cuts the middle out of a long message; when the cut part matters, such as a closing report's list of findings, print that message in full with `--at "<the time printed on its line>"`. If this check already ran earlier in the session, check only the work since then, plus whatever that run reported as still needing action or waiting on others. If the earlier part of the session was handed off to another session with a written record, check only the work after the handoff, plus anything that record left with this session.
2. List every request the user made, every step Claude gave them, every question still unanswered, and everything Claude said it would do. Reread the text of each message the session sent (an email, a chat post, a comment) and list every ask of someone else and every promise in it, because Claude's own summary of a sent message can leave them out. If the session followed a written process (an article, a checklist, a skill), list that process's own steps too, not only the ones the session mentioned; a skill's closing steps count, such as the record file it keeps of sent replies. A question Claude asked counts only when its answer could change the work. A waiting item carried in from a handoff or a record file counts too; confirm it at the thread or task it lives in before calling it open, because the record can be stale. Findings that an audit or review reported earlier in this session and left for the user's yes or no count as well, even when the audit's own ledger records them: they go under Needs you, and the verdict is "Not yet."
3. Confirm each one at its source, not from memory: the file, thread, task, or event itself. An item this session already read back counts, unless it could have changed since. A screenshot or export of the result, supplied during the session, counts as reading it back. Something the session itself reported as unconfirmed or untested is checked now when a read-only check exists; when none does, it goes under Couldn't check. When the session rebuilt or replaced a file it had already handed out (attached to a task, sent in a message), confirm the current version at each place it was handed out; a search of the task tool and chat for the file's name finds those places. When a connector fails, read the item another way (its API with a stored key, the browser) before listing it under Couldn't check. Check that work is committed and pushed, that background jobs, servers and watchers the session started have finished or been stopped, and that files worth keeping aren't only in a temporary session folder. To find those jobs, list the session's own background tasks and processes, including a command that moved to the background part-way through. When looking for leftover processes, count only what this session's tool calls started; a system process the session never ran (a window server, a virtual machine) is not a leftover. In a repo other sessions also write to, judge only the files this session's tool calls changed, not the whole `git status`. When another session has written to the same repo or ledger since this session's change, confirm the change is still in the published result (for example `git merge-base --is-ancestor <commit> origin/main`), and recheck each finding a ledger lists at its source, since the other session may have settled it. Work done by a session this one started is confirmed the same way, at its commit, branch, task or live result and not from its final report; search the record files it wrote for loose ends noted without a reminder (a "no task yet" line). Uncommitted edits in a repo that an automatic backup job commits on a schedule count as handled; only a repo with no such job needs them committed and pushed. When you know which places such a job covers, count edits there as handled without looking the job up again. For any other repo whose instructions claim such a job, look at its newest automatic commit: when that is older than a few of the job's intervals, the job has stopped, so the edits need committing and the stalled job gets one line. An empty search proves nothing: to-do searches often skip completed items, so check the completed or archived view (a logbook) before deciding a to-do is still open or was never made. Read a logbook or a day's list narrowly: the shortest period that covers the item (usually a day or two), a limit of about 15, and a project filter when the item's project is known, because a wide read returns dozens of full to-dos to confirm one. Widen the read only when the item is not in it.
4. For anything waiting on another person or a later date, look for its reminder: a to-do in their task manager, or a calendar event. With no reminder, it counts as something the user needs to act on. A promise made during the session to do something by a date is waiting on that date and needs a reminder too, whether or not it was part of the requested work; in a scoped check, something promised for today outside the scope gets one line after the verdict and does not change it. A work task counts only if it has a due date. Anything else counts only if it will bring the item back without anyone having to remember it, such as a help desk conversation snoozed to a date, a project's to-do file that its own process reads, or a recurring routine's log that carries open items forward; a tag, an assignment or a status with no date (Pending, Active) doesn't count. A reminder due today or earlier counts as none, and so does an item tied to a later event today that has no reminder of its own. Look for a reminder by the subject line or title of what was sent as well as by the names of the people involved, and for a repeating to-do read today's list or the logbook instead of a title search, which fills with projected repeats; a repeat that next comes up on a later day is in the list of repeating templates, which is long, so filter it by title or project instead of reading it whole. A meeting or calendar block on a later day that the item rides on counts, and so does a documented hand-off that moves the item to someone else, such as a task handed to code review; a check that exists only in this session counts only with the caveat that it ends when the app quits. An item whose answer arrives on its own in a place already read every day, where no answer means nothing is left to do (a submitted job application), goes under Waiting on others with that place named and does not change the verdict. A message sent in the session whose non-reply would leave work undone needs a dated reminder of its own; a thread that reopens on a reply covers only the case where the reply comes. Work the session was told to park or defer stays out of the verdict like anything skipped, but gets one line saying where its record lives, with an offer of a reminder only when no record exists anywhere. If you have no way to look, list it under Couldn't check.

## Reply

Line one is the verdict. "✅ Yes, you're done for now." means nothing needs them; always start it with the ✅, which is their visual cue that they can leave. Otherwise, write "Not yet." Never open with yes when something needs them, however small. If one of their questions went unanswered, answer it right after the verdict.

Then give these groups, leaving out any that are empty:

- **Needs you:** exact steps, in order.
- **Waiting on others:** who, what, and where the reminder is.
- **Couldn't check:** what, and why, only where the answer could change the verdict. A step reported as done that cannot be read back goes here only, and does not change the verdict.
- **Safe to delete:** each file or folder in `~/Downloads` or on the Desktop that he handed to this session, or that the session wrote there, and that is now filed, sent or a copy of something in Gmail. Full path, one per line. If one should be kept, say which and why. Look for a handed-in screenshot with `find -name` and a pattern that stops before the AM or PM: macOS puts a narrow no-break space there, so a typed-out name matches nothing.

Leave out suggestions, polish, and anything optional. List only what the work they asked for requires.

Change nothing except the log below. If Claude can finish an item itself, such as creating a missing reminder, end with one question asking whether to. A closing record that another skill or a project rule requires and that is missing (a reply skill's record of a sent reply, a skill's reflect note, a project's log of sent emails) is such an item: it goes under Needs you, and the closing question offers to write it.

## Reflect and improve (suggest only)

Do this after the checks and before writing the reply, because the reply has to be the last thing in the turn. It runs even when the checks failed or stopped early. Never edit this `SKILL.md` or change how the skill works; only write to `~/.claude/skills/done/improvement-log.md`, newest entry on top, creating it if it doesn't exist.

- **Every run:** a dated note of one to three lines on what got in the way. Examples: a source that could not be checked, and why (a connector missing on this account); a waiting item with no obvious place to look for its reminder; `session_text.py` failing or printing too much to read; an item the user had already handled or didn't care about. If a later message shows the verdict was wrong, add that to the entry, because a missed item is the most useful thing this log can hold. "No notable friction" is a valid note.
- **Keep it free of names.** This skill runs in all kinds of sessions, so describe the kind of item ("a task", "an email reply"). Never quote the session or name a person.
- **Synthesis:** when there are 10 or more notes since the last synthesis, or the last synthesis is over 30 days old and at least one new note exists, read those notes and add a dated `## Synthesis` entry at the top with a short prioritized list of proposed refinements, each tagged `STATUS: AWAITING REVIEW`. Apply none of them. If it adds proposals, say so in one line at the end of the reply.
